## 1. 架构总览

```
                    ┌─────────────────────────────────────────────┐
                    │  cmd/action  (Phase 1 唯一 CLI 入口)          │
                    │  · 捕捉 error · 优雅输出日志 · 禁止 panic      │
                    └───────────────────────┬─────────────────────┘
                                            │
        ┌───────────────────────────────────┼───────────────────────────┐
        │  pkg/ (核心资产层，与运行环境严格解耦)                          │
        │                                                               │
        │  config ──► lang ──► ast ──► index ──► engine ──► llm/meta    │
        │  (嗅探)    (解析)   (提取)   (索引)    (漏斗+查询)  (外部语义)  │
        └───────────────────────────────────────────────────────────────┘
                                            │
                         Storage / VCSClient 接口（内存｜Postgres｜Neo4j）
```

**数据流（Phase 1）**：
`嗅探 go.mod/pom.xml → 加载 .scm → tree-sitter 解析 → 提取 EntryNode/CallNode/DBOp → 建正向/反查/排查索引 → Funnel 过滤 → 输出两个查询结果`

**设计铁律**：
1. `pkg/` 里的包**绝不感知** `cmd/` 的运行环境；`pkg/ast` 只提取结构化数据，**不掺告警组装**；`pkg/engine` 组合数据 + 执行漏斗。
2. 错误处理：业务逻辑**严禁 panic**，统一 `fmt.Errorf("...: %w", err)` 上抛，仅 `cmd/action/main.go` 捕捉。
3. 所有外部依赖（LLM、GitHub、元数据源、存储）**必须接口化**，便于 Mock 和切换。
4. 无状态：MVP 阶段所有索引纯内存（原生 map/slice），随 Docker 容器销毁。

## 3. 核心数据结构（索引 = 系统 of record）

```go
// EntryNode：一个业务入口
type EntryNode struct {
    ID          string            // 稳定 ID（如 "http:GET:/api/order"）
    Kind        EntryKind         // HTTP | GRPC | KafkaConsumer | XXLJob | Cron
    Name        string            // 入口名称（路径/method/topic/job name）
    Handler     Symbol            // 处理函数（pkg.Func + 位置）
    SourceLoc   Loc               // 源码位置
    PodHints    []string          // P2: 运行单元归属线索（代码门控/命名规则）
}

// CallNode：一次调用（构建正向调用链）
type CallNode struct {
    Caller      Symbol            // 调用方函数
    Callee      Symbol            // 被调方（函数/方法/外部依赖）
    Kind        CallKind          // DB | Redis | Lock | MQ | HTTP | GRPC | ThirdParty | Func
    Loc         Loc               // 调用点位置
    Args        []string          // 关键实参（表名/key/topic/URL 等字面量）
}

// DBOp：下游数据库/存储操作（"下游操作分析"核心）
type DBOp struct {
    EntryID     string            // 归属入口
    Op          OpKind            // Read | Write | Delete
    Resource    string            // table 名 / key 模式
    Fields      []string          // 涉及字段
    Where       string            // WHERE 条件近似（或近似 SQL）
    InLoop      bool              // 是否在循环内 ← L1 高危规则"循环内查库"
    InTx        bool              // 是否在事务内
    UnderLock   bool              // 是否持锁调用
    InGoroutine bool              // 是否在协程内
    Loc         Loc
}
```

**三张索引（全部纯内存 map，可序列化）**：
```go
// 正向索引：函数/入口 → 调用链
type ForwardIndex map[Symbol][]CallNode

// 反查索引：资源 → 入口（"反向影响查询"，区分读写）
type ReverseIndex map[ResourceKey][]Ref
type ResourceKey struct { Kind string; Name string }  // kind ∈ {table,key,config,method,topic,error}
type Ref struct { EntryID string; Op OpKind; Loc Loc }

// 排查索引：错误码/日志模板/超时/枚举 → 源码位置
type TroubleIndex map[string][]Loc  // key ∈ {"err:10001", "log:xxx", "timeout:yyy", "enum:zzz"}
```

## 4. 接口定义（Interface 隔离）

```go
// LLM：L3 业务语义定性（P1 默认 noop，P2 接入，可切 OpenAI/Claude/Qwen/私有）
type RiskAnalyzer interface {
    // 输入：命中高危的 AST 链路 + 业务标签；输出：风险定性 + 业务影响摘要
    Analyze(ctx context.Context, chain []CallNode, meta []BusinessTag) (*RiskReport, error)
}

// 业务元数据源：YApi / proto 注释 / TiDB 表结构 / XXL 管理端（每家私有部署不同）
type MetadataSource interface {
    Fetch(ctx context.Context, ref ResourceKey) ([]BusinessTag, error)
}

// 代码托管：GitHub（P1）/ GitLab / 云效（P2）
type VCSClient interface {
    GetPRDiff(ctx context.Context, repo, pr string) ([]FileDiff, error)
    PostComment(ctx context.Context, repo, pr, body string) error
}

// 存储：内存（P1）/ Postgres（P2）/ Neo4j（P3），同一接口
type Storage interface {
    Save(ctx context.Context, idx *Index, key string) error
    Load(ctx context.Context, key string) (*Index, error)
}
```

## 5. 关键工程决策

### 5.1 去 cgo（优先处理）
- `smacker/go-tree-sitter` 依赖 CGo → 拖累 Docker 镜像与交叉编译。
- **改用纯 Go 绑定 `github.com/tree-sitter/go-tree-sitter`（无 cgo）**，Dockerfile 从"多阶段 + C 工具链"简化为单阶段。

### 5.2 依赖版本
- `github.com/google/go-github/v60/github`（v50 已旧，Marketplace/OAuth 会用到新版特性）
- `gopkg.in/yaml.v3`（配置）
- `golang.org/x/mod/modfile`（Go 嗅探）+ 新增 `pom.xml` 解析（Java 嗅探，可先手写轻量解析器或引入 maven 解析库）

### 5.3 语言策略（实现 vs 目标）
- **实现语言**：Go 1.21+（强制，不变）
- **目标语言**：Java 优先 + Go。`.scm` 分 `go/` 和 `java/` 两个目录；`lang/` 包做 parser registry 统一装载。

### 5.4 Funnel Filtering（L0/L1/L2 规则示例）
- **L0（物理过滤）**：`*_test.go`、`Test*.java`、`vendor/`、`node_modules/`、`docs/`、生成代码（`*.pb.go`/`*_gen.go`/MyBatis 生成器产物）——直接跳过。
- **L1（本地 AST 高危规则，命中即标记）**：
  - 循环内查库（`DBOp.InLoop`）→ 高危
  - 事务内调用外部 HTTP/gRPC（长事务风险）
  - 持锁调用远程依赖（`UnderLock` + 远程）
  - 无 WHERE 的 UPDATE/DELETE（全表风险）
- **L2（复杂度 + 注释校验）**：函数圈复杂度阈值、关键路径注释缺失——作为 L3 的筛选权重，不直接告警。
- **L3（LLM 深度定性）**：仅将 L1 命中的链路 + 业务标签喂给 LLM，产出风险等级 + 业务影响摘要。

## 7. Phase 1 实现要点清单

1. `config/`：嗅探 `go.mod`（`x/mod/modfile`）+ `pom.xml`，判定生态 → 返回要加载的 `.scm` 列表。
2. `lang/`：parser registry，按文件扩展名选 grammar，纯 Go 绑定。
3. `ast/`：遍历 AST，产出 `EntryNode` / `CallNode` / `DBOp`，**只提取、不组装告警**。
4. `index/`：由 ast 产出构建三张内存索引 + `Serialize()`。
5. `engine/`：`funnel.go` 跑 L0/L1/L2；`query_impact.go` 与 `query_trouble.go` 分别服务"改前/改中"两个入口。
6. `llm/` + `meta/`：P1 提供 `noop` 实现，接口先定死。
7. `cmd/action/main.go`：唯一 panic 捕捉点；统一 `fmt.Errorf("%w")` 上抛后优雅输出。
