# 多语言适配器（下一个：Java）

> 结论：**不要再单独做一套引擎。** 保留一个 core（IR + 规则 + 索引 + 报告），把语言差异收敛到 Adapter。Go 是第一个适配器，Java 是第二个。

---

## 1. 现在哪些是 Go 专属的

与语言无关、可复用的部分：

- `pkg/ast/types.go`：IR（`EntryNode` / `CallNode` / `DBOp` / `FuncSummary` / `Trouble`）
- `pkg/index`：正向 / 反查 / 排查索引
- `pkg/engine`：R1–R11 规则、上下文传播、policy
- `pkg/diff`、`pkg/impact`、`pkg/report`、`pkg/baseline`、`pkg/semantic`
- `pkg/profile`：库画像

Go 专属、应该收进适配器的部分：

- `pkg/ast/query.go`：Gin / GORM / gRPC / Kafka 提取
- `pkg/ast/extract.go`：Go AST 遍历、接收者类型推断、循环/事务/锁上下文
- `pkg/ast/middleware.go`：Gin `.Use` / `Group` 解析
- `pkg/ast/queries/go/*.scm`
- `pkg/config`：`go.mod` 嗅探
- `pkg/lang`：目前只是 Go 的薄注册表

---

## 2. 目标结构

```
cmd/topolink
   │
   ▼
pkg/lang.Registry
   ├── golang.Adapter    queries/go/*.scm + Go AST + Gin/GORM
   └── java.Adapter      queries/java/*.scm + Java AST + Spring/MyBatis
   │
   ▼
pkg/ast (只放 IR)  ──►  pkg/index  ──►  pkg/engine  ──►  pkg/report
```

适配器只负责把源码变成同一套 IR；规则、索引、diff、impact、baseline、语义层完全不动。

---

## 3. 适配器接口

```go
package lang

type Adapter interface {
    Name() string
    Extensions() []string
    Sniff(root string) ([]string, error) // 该仓库应加载的 .scm
    Parse(path string) (tree *sitter.Tree, src []byte, err error)
    NewExtractor() ast.Extractor
}

type Extractor interface {
    Extract(path string, tree *sitter.Tree, src []byte) ast.Result
    Resolve(results []ast.Result) // 路由 + 中间件，按语言各自实现
}
```

`ast.Result` 已经包含 `Entries` / `Calls` / `Ops` / `Funcs` / `Troubles`，合并点很稳定。

---

## 4. 改造步骤

1. 把 Go 提取器搬到 `pkg/lang/golang`（纯移动，`pkg/ast` 只留 IR 和共享工具）。
2. 引入 `lang.Registry`：`ForFile(path)` / `ForRepo(root)`。
3. `config.Sniff` 返回 `{Language, RuleFiles}`：
   - `go.mod` → Go
   - `pom.xml` / `build.gradle` / `*.java` → Java
4. `cmd/analyze.go`：按文件选适配器，收集各语言的 `[]ast.Result`，各自 `Resolve`，最后合并进同一个 `index.Build`。
5. 新增 `pkg/lang/java` 与 `queries/java/*.scm`。
6. R1–R11 保持不变；Java 专属规则也在 `pkg/engine` 里基于 IR 增加。

前 4 步是纯重构，Go 行为保持不变；第 5 步才开始真正增加 Java 覆盖。

## 5. Java 映射

| Java 结构 | 产出 IR |
|---|---|
| `@RestController` + `@GetMapping` / `@PostMapping` | `EntryNode`（HTTP），路径 = 类 + 方法 mapping |
| `@Transactional` | 下游操作 `InTx = true` |
| MyBatis `<select>` / `<insert>` / `<update>` / `<delete>` | `DBOp`（表名 + WHERE） |
| Mapper 接口方法 | 关联到 XML statement |
| `@DubboService` / `@DubboReference` | `EntryNode`（RPC）/ 远程调用 |
| `@XxlJob("name")` | `EntryNode`（`XXLJob`） |
| `RedisTemplate` / `@Cacheable` | `CallRedis` / 缓存资源 |
| `synchronized` / `ReentrantLock` / Redisson | `UnderLock` |
| `@KafkaListener` | `EntryNode`（`KafkaConsumer`） |
| `restTemplate` / Feign | `CallHTTP` |

开源 core 先做 Spring MVC + MyBatis + JDBC；Dubbo、XXL-Job、Nacos/Apollo、YApi/TiDB、分库分表放 pro 适配器。

## 6. 开源 / pro 边界

| 层 | 开源 core | Pro |
|---|---|---|
| Go 适配器 | Gin/Echo/Chi/Iris/net/http/GORM/gRPC/Kafka | — |
| Java 适配器 | Spring MVC、MyBatis、JDBC、`@Transactional` | Dubbo、XXL-Job、Nacos、Apollo、YApi、TiDB、分库分表 |
| 跨服务 | — | gRPC 方法级、Kafka 生产消费配对 |
| 图存储 | 内存 | Neo4j |

开源适配器负责证明"IR 和规则是语言无关的"；pro 适配器负责中国栈变现。

---

## 7. 为什么不单独做一个仓库 / 引擎

- 护城河是 **IR + 规则 + 爆炸半径体验**，不是 parser。第二套引擎会重复索引、规则、报告、baseline、语义缓存。
- 一套 IR 才能做**跨语言爆炸半径**（Go 服务通过 gRPC 调 Java 服务）。
- 新语言 = 新适配器 + 新 `.scm`，不是新产品。

## 8. 工作量估算

| 里程碑 | 工作量 |
|---|---|
| 适配器 seam + 搬 Go 提取器（行为不变） | 1–2 天 |
| Java grammar + Spring MVC 入口 + 基础调用 | 3–5 天 |
| MyBatis XML → `DBOp`（表名/WHERE） | 3–5 天 |
| `@Transactional` / 锁 / Kafka / Dubbo（pro） | 1–2 周 |

第一个 Java 里程碑只需要产出同样的 IR，现有 R1–R11 就能直接复用。
